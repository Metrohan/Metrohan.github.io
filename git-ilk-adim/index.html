Git nedir?

Dosyalarındaki her değişikliği kaydeden, ücretsiz ve açık kaynak bir sürüm kontrol sistemi.

Neden yazıldı? Linux çekirdeğinin binlerce geliştiricisinin kullandığı araç artık ücretsiz kullanılamayınca Linus, Linux'un kurucusu olarak kendi aracını birkaç haftada yazdı.

  • Geçmiş: her kayıtta neyin, kimin, ne zaman ve neden değiştiğini saklar.
  • Geri dönüş: bozulursa çalışan eski hâle dönersin.
  • Deneme: branch ile çalışan sürüme dokunmadan yeni fikir dene.
  • Ekip: aynı projede birçok kişi aynı anda çalışır, değişiklikler birleşir.
Dağıtık: projeyi indiren herkesin bilgisayarında geçmişin tam kopyası vardır. İnternet olmasa da çalışırsın; bir bilgisayar bozulsa geçmiş kaybolmaz.
Git ile yönetilen bazı projeler: LinuxAndroidPythonVS Codeve büyük ihtimalle sonraki işyerin
Git'i 2005'te Linux'un yaratıcısı Linus Torvalds yazdı. Linux çekirdeği o zamana kadar BitKeeper adlı ticari bir aracı ücretsiz kullanıyordu; bu izin kaldırılınca Linus kendi aracını yazdı ve ilk sürüm birkaç haftada çalışır hâle geldi. Temmuz 2005'ten beri projenin bakımını Junio C. Hamano yapıyor. Git ücretsiz ve açık kaynaktır (GPLv2). Stack Overflow'un geliştirici anketlerinde katılımcıların yaklaşık %94'ü Git kullandığını söylüyor. "Dağıtık" kelimesini vurgulayın: merkezî bir sunucuya bağlı kalmadan, herkesin elinde tam geçmiş var. GitHub ise bundan yıllar sonra (2008) kurulan ayrı bir şirket ve site; bir sonraki slayt.

Git ve GitHub aynı şey değil

Git

Bilgisayarına kurduğun program. Geçmişi kaydeder, branch açar, sürümleri karşılaştırır. İnternet olmadan da çalışır.

git push
git pull

GitHub

Git depolarını internette saklayan site. Kodunu yedekler, Issue ve Pull Request ile ekipçe çalışırsın. Benzerleri: GitLab, Bitbucket.

Gerçek hayatta: Git fotoğraf makinesi, GitHub bulut albüm. Fotoğrafı makineyle çekersin; albüme yüklersen başkaları da görür. Albüm olmadan da fotoğraf çekebilirsin.
En sık karışan iki kavram. Git yerelde, GitHub uzakta. Sunumun ilk büyük kısmı Git, sonrası GitHub.

Örnek bölümünde imzanın neden bu kadar önemli olduğunu göreceğiz.

Dört alan: bir değişikliğin yolculuğu

Bir değişikliği kargo paketi gibi düşün. Her komut onu bir sonraki durağa taşır.

Çalışma alanı

working directory
Kargo: masadaki eşyalar

Durum: untracked (yeni) ya da modified (değişti)

Hazırlık alanı

staging area
Kargo: koliye koyduklarım

Durum: staged, sonraki commit'e girecek

Yerel depo

local repository
Kargo: bantlı, etiketli koli

Durum: committed, kayıtlı

Uzak depo

remote (GitHub)
Kargo: teslim edildi

GitHub'daki ortak kopya.

dosya.txt ✎
git add
git commit
git push
← restore --staged
← git pull
Kaybolduğunda: git status değişikliğin hangi durakta olduğunu söyler: kırmızı = henüz seçilmedi, yeşil = commit'e hazır.
Sunumun en önemli slaytı. Her adımda dosyanın bir sonraki durağa geçişini gösterin ve komutu sesli söyleyin. Adım 4: ters yönler. restore --staged koliden geri çıkarır, pull GitHub'daki paketleri bilgisayara getirir. "Hazırlık alanı neden var?" sorusu gelirse: masada beş eşya var ama bu koliye sadece ikisi girecek.

Commit, oyundaki kayıt noktası gibidir

Boss savaşından önce oyunu kaydedersin; kaybedersen kayıttan devam edersin. Commit de projenin o anki hâlini adıyla kaydeder.

Ne değişti? Commit hangi satırların değiştiğini bilir.
Kim, ne zaman yaptı? Yazar ve tarih otomatik eklenir.
Neden yapıldı? Bunu sen yazarsın: commit mesajı.
Git'in temel fikri bu: projenin anlık fotoğraflarını sırayla saklamak. Her kayıt bir durak; duraklar bir hat oluşturuyor. Bu soruna "sürüm kontrolü" (version control) denir.

Commit yalnızca hazırlık alanındakileri kaydeder ve sadece senin bilgisayarındadır; GitHub'da görmek için push gerekir. Her commit'in benzersiz bir kimliği (hash) var ve bir öncekine bağlı; hat bu bağlardan oluşur. -a seçeneği yeni (untracked) dosyaları eklemez.

git restore: geri al

restore --staged: hazırlık alanını son commit'e eşitler, yani seçimi geri alır. Dosyadaki değişiklik kalır.
restore: dosyayı hazırlık alanındaki hâline döndürür. Add etmediysen bu, son commit'teki hâl: oyunda son kayıttan başlamak gibi.
$ git restore --source=a1b2c3d main.py# dosyayı daha eski bir commit'teki hâline getir
Dikkat: git restore dosya commit edilmemiş değişiklikleri siler, geri getirilemez. Önce git diff ile bak.
İki restore'u karıştırmamak önemli: --staged güvenli (sadece seçimi geri alır), --staged olmadan ise dosyadaki değişikliği atar. Sık commit atmanın faydası burada: son kayıt ne kadar yeniyse kaybedilen iş o kadar az. Eski kaynaklarda git checkout -- dosya görürler; aynı işi yapar.

Branch: çalışan sürümü bozmadan dene

main her zaman çalışan sürüm kalsın. Yeni iş ayrı bir hatta ilerler; dosyalar kopyalanmaz.

terminal
$ git switch -c feature/yeni # aç ve geç$ git commit -m "…" # bu hatta$ git switch main # ana hatta dön$ git branch # hatları listele feature/yeni * main
  • switch -c ad yeni hat açar ve oraya geçer. HEAD onunla gider.
  • Yeni commitler sadece HEAD'in olduğu hatta eklenir.
  • switch ad hatlar arasında geçer; klasördeki dosyalar o hattın hâline döner.
  • * bulunduğun hat. Adlandırma: feature/…, fix/…
Gerçek hayatta: dükkan açıkken rafları söküp yeniden dizmezsin; yeni düzeni depoda denersin. Commit edilmemiş değişiklik varken branch değiştirirseniz Git uyarabilir; önce commit edin. Eski kaynaklarda git checkout -b görürler; aynı işi yapar.

git merge: hatları birleştir

Fast-forward

main'e yeni bir şey eklenmediyse Git sadece main tabelasını ileri kaydırır.

Merge commit

İki hat da ilerlediyse Git ikisini birleştiren merge commit (aktarma durağı) oluşturur.

$ git switch main # hedefe geç$ git merge feature/yeni$ git branch -d feature/yeniDeleted branch feature/yeni.
$ git log --oneline --graph* 5c6d7e8 Merge branch 'feature/yeni' |\ | * 3a4b5c6 Yeni özellik * | 8d9e0f1 main'de başka iş |/ * 3f9a1c2 Arama özelliğini ekle
Kural: birleşmeyi alacak hatta geç, sonra merge et. İş bitince branch silinebilir (-d): commitler main'de kaldığı için hiçbir şey kaybolmaz. --graph çıktısı metro haritasının terminaldeki hâli.

git rebase: commitlerini yeni tabanın üstüne taşı

merge

Geçmişi olduğu gibi korur, aktarma durağı ekler. Güvenli; ekipte varsayılan.

rebase

Commitleri main'in ucuna yeniden dizer; geçmiş tek çizgi olur. D′ ve E′ yeni commitlerdir, kimlikleri değişir.

$ git switch feature/yeni$ git rebase main # ucuna taşı# conflict çıkarsa: düzelt, sonra$ git add dosya && git rebase --continue$ git rebase --abort # vazgeç
Altın kural: sadece kendi, henüz push etmediğin commitleri rebase et. Başkalarının kullandığı commitleri yeniden yazarsan geçmişleri karışır.
git pull --rebase: yerel commitlerini, GitHub'dan gelenlerin üstüne dizer.
Gerçek hayatta: sırada beklerken önüne yeni insanlar girdiyse, merge "iki sırayı birleştir" demek; rebase ise "beni sıranın en sonuna al" demek. Sonuç aynı içerik ama geçmiş farklı görünür. Rebase sonrası main'e merge fast-forward olur. Başlangıçta merge yeterli; rebase'i ekip kuralı izin veriyorsa ve sadece kendi yerel branch'inde kullanın. Push edilmiş bir branch'i rebase ettikten sonra tekrar göndermek force push gerektirir; bunu yeni başlayanlar yapmamalı.

Gerçek hayatta: iki kişi aynı formu farklı doldurmuş. Görevli tahmin etmez, sorar. Git de "hangisi doğru?" diye soruyor.
<<<<<<< HEADbaslik = "Hoş geldin"
Bulunduğun hattın sürümü
=======baslik = "Merhaba">>>>>>> feature/yeni
Gelen hattın sürümü

Farklı satırlardaki değişiklikleri Git kendisi birleştirir; conflict sadece aynı satır değiştiğinde çıkar. Conflict bir hata değil, bir soru. Çözüm sırasında git status, conflict olan dosyaları "both modified" diye gösterir. VS Code gibi editörlerde "Accept Current / Accept Incoming / Accept Both" düğmeleri aynı işi yapar. Emin değilseniz git merge --abort her şeyi merge öncesine döndürür.

Uzak depo: clone, push, pull

$ git remote add origin URL # bağla, bir kez$ git push -u origin main # ilk gönderim$ git push # sonrakiler$ git pull # yenilikleri al$ git clone URL # depoyu indir$ git remote -v # bağlantıyı gör
  • push commitlerini GitHub'a gönderir. Commit edilmemiş değişiklik gitmez.
  • pull GitHub'daki yeni commitleri alır ve bulunduğun hatta birleştirir.
  • clone depoyu bütün geçmişiyle indirir; origin bağlantısı hazır gelir.
  • Kural: işe başlamadan pull, iş bitince push.
Gerçek hayatta: ortak Drive klasörü gibi, ama kendiliğinden eşitlenmez; göndermek ve almak için komut yazarsın. origin sadece bir takma ad, telefon rehberine numara kaydetmek gibi. -u, bulunduğun hattı uzak hatla eşler; sonra sadece git push yeter. git fetch: indirir ama birleştirmez; pull = fetch + merge. Push reddedilirse (rejected) GitHub'da senin almadığın commit var: önce pull.

Issue: yapılacak işin kaydı

Boş şifreyle girişte program çöküyor #12
Openkullanici açtı · bug · atanan: ekip-arkadasi

Ne oldu?

Şifre alanı boş bırakılıp Giriş'e basınca program kapanıyor.

Nasıl tekrarlanır?

python main.py → kullanıcı adı yaz → şifre boş → Giriş

Beklenen

"Şifre boş olamaz" uyarısı çıksın.

  • Başlık ve numara: her issue'nun numarası var, #12 diye anılır.
  • Etiket (bug, özellik) ve sorumlu kişi.
  • İyi açıklama: ne oldu, nasıl tekrarlanır, ne bekleniyor.
  • Commit ve PR'da #12 yazınca bağlanır; PR'da Closes #12 merge olunca issue'yu kapatır.
Gerçek hayatta: teknik servis fişi. "Buzdolabı soğutmuyor; dün başladı; fişi takıp çıkardım."

Ekip akışı: Issue'dan pull'a sekiz durak

1. Issue

Yapılacak iş yazıya dökülür ve birine atanır.

# web: Issues → New issue$ gh issue create # isteğe bağlı

2. Branch

Önce main'i güncelle, sonra işe özel bir hat aç. Adında issue numarası olsun.

$ git switch main && git pull$ git switch -c fix/sifre-12

3. Commit

Yerel döngü: düzenle, çalıştır, status, diff, add, commit.

$ git add main.py$ git commit -m "Boş şifre kontrolü ekle (#12)"

4. Push

Branch'i GitHub'a gönder. İlk seferde -u.

$ git push -u origin fix/sifre-12

5. Pull Request

GitHub'da Compare & pull request. Açıklamaya Closes #12.

$ gh pr create --fill # isteğe bağlı

6. Review

Ekip arkadaşın okur, yorum yazar. Düzeltip aynı branch'e push edersin; PR güncellenir.

$ git commit -am "Uyarı metnini düzelt (#12)"$ git push

7. Merge

Onaydan sonra Merge pull request. Issue #12 otomatik kapanır.

# web: Merge pull request$ gh pr merge --merge --delete-branch

8. Pull

Herkes main'i günceller; biten branch yerelde silinir.

$ git switch main && git pull$ git branch -d fix/sifre-12
Her adımda treni bir durak ilerletin. Kural: main'e doğrudan commit atılmaz; her iş bir branch ve bir PR ile gelir. Böylece main her zaman çalışan sürüm olur ve her değişikliği en az iki kişi görmüş olur. Açık kaynak projelere katkı da aynı akışla yapılır.
